# DiskEye v0.9.3 — "窗口打不开/看不到 tab" 根修（2026-09-16）

## 现象（用户两次反馈）

1. "7 个 tab 一个没删，但是界面上看不到！"
2. "v91 开了半天 tab/排行榜确认没有""只有自己一个进程？"

## 排查（三个问题叠加，逐层剥离）

1. **排行榜空白** = v0.9.1 榜单合并查询 NRE（进程只在 write_bytes 有、events 没有 → 解引用 null → 后台异常被静默吞）→ v0.9.2 修复，实测修复后榜单 76 进程。
2. **tab 看不到** = 用户仍看 v0.9.1 实例（榜单坏）+ 窗口本身不可见。UIA 枚举 Descendants=0 触发深查。
3. **真正根因（Win32 原生枚举实证）**：窗口所有 9 个子控件（SysTabControl32、7 个 tab、搜索栏）完整存在，但 rect 全部 `@-21333,-21333`（DPI 150% 下的 -32000 最小化/屏外位置）——**窗口的"还原位置"被记到了虚拟屏外**；托盘 ShowMainForm 只调 Show/Activate，不还原最小化、不校验位置 → 窗口永远出不来。SW_RESTORE 也救不回（RestoreBounds 本身在屏外）。

## 修复（v0.9.3）

- `MainForm.RestoreToScreen()`：托盘/管道打开的统一入口——还原最小化 + 检测窗口与任何屏幕不相交则搬回主屏居中。
- 启动位置恢复：config 坐标在屏外则忽略（居中）。
- `SaveWindowPos`：只保存与屏幕相交的位置（坏坐标永久进不了 config）。

## 验证

- Win32 EnumChildWindows：修复前 9 控件全在 `@-21333`；0.9.3 启动后 TabControl `847x571@620,267` 屏内。
- 截图实证：标题"● 精确归因（ETW）"、搜索栏、"凶手指控榜"表格 rustc.exe 第一，node/nvcontainer/dotnet/link/crossgen2/chrome/微信/抖音等几十个进程在榜。
- 67 xunit 绿。0.9.3 已替换运行实例（保留当日库），publish_v93 归档。

## 教训

- "UI 响应正常"≠"窗口在屏上"。UI 探针（WM_NULL）与 UIA Descendants 结果矛盾时，必须下沉到 Win32 EnumChildWindows 看 rect。
- 用户说"界面上看不到"这类感官报告要优先于程序化探测结果——探测脚本"证明"窗口正常时，先质疑探测是否测对了层。
