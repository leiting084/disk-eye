# DiskEye v0.8.1 — 单 exe 双角色 + 绿色版数据跟随（2026-08-29）

## 一句话

按用户反馈把 v0.8 的两个交付文件合成**一个 exe**（`--etw-child` 自启动子进程模式），配置/数据库/日志全部跟 exe 走（绿色版），并修掉发布版归因慢的时序问题。

## 用户反馈 → 改动

| 反馈 | 改动 |
|------|------|
| "怎么又两个程序" | 删除独立 `DiskEye.Etw` 项目。主程序 `DiskEye.exe --etw-child <父PID>` 即子进程，隔离性不变，交付只有一个 exe。实测子进程内存 ~44MB（WinForms 程序集惰性加载，不初始化 UI 就不占） |
| "配置文件为什么不跟着程序走" | `AppConfigStore.ConfigDir` 改为 exe 同目录（探测可写性，只读目录回落 LocalAppData）；首次启动把 `%LOCALAPPDATA%\DiskEye\` 的 config.json + events.db* 拷贝迁移过来（不删旧数据） |
| （实测发现）发布版归因退化成启发式 | 发布版子进程（单文件自解压 + TraceEvent 初始化）EV 延迟 ~2s，超过 2s 匹配窗口 → 窗口放宽到 3s、缓存 TTL 到 4s |

## 实现要点

- `Program.Main` 最前面分流 `--etw-child`：子进程模式直接进 `EtwChildWorker.Run()`，**在 Mutex / WinForms 初始化之前**，不碰任何 UI
- `EtwChildProvider` 子进程路径改为 `Environment.ProcessPath`（自己），删掉 LocateChildExe
- TraceEvent 包挪进主 csproj
- 意外收获：主程序被杀后子进程 60s 冷却自动重启（MaxRestarts 3 次）的路径也实测通过了

## 已知边界（不变）

- 存活 <1s 的进程：pid 精确，名字可能 unknown
- `Deleted` 事件走启发式（ETW FileIo/Create 不覆盖删除）
- 两个 DiskEye.exe 同名进程在任务管理器里要靠命令行区分（`--etw-child` 是子进程）
