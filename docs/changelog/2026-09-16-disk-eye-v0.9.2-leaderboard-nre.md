# DiskEye v0.9.2 — 排行榜空白修复（2026-09-16）

## 现象（v0.9.1 实测）

用户：主窗口排行榜"只有 DiskEye 自己一个进程"，tab/排行榜像没内容。

## 根因（v0.9.1 引入的 NRE）

v0.9.1 新增的榜单合并查询 `QueryProcessUnified` / `QueryFolderUnified` 用两趟查询：
先查 events 建字典，再用 write_bytes 合并。合并时：

```csharp
rows.TryGetValue(n, out var cur);
rows[n] = new UnifiedRow(n, cur.Path, cur.EventCount, ...);   // cur 可能为 null
```

`UnifiedRow` 是 class；当某进程**只在 write_bytes 有真实写入、今天 events 表没有行**
（chrome/飞书/微信/nvcontainer 等正是这种——写字节但生命周期事件落在别的窗口/被目录过滤），
`cur=null` → 访问 `cur.Path` 抛 **NullReferenceException**。
异常发生在后台 Task，被 catch 静默写 Debug，**整个榜单填充被跳过**，只剩少数"两个表都有"的进程（DiskEye 自己写库所以两个表都在）。

ETW 采集本身完全正常（write_bytes 2700 行、76 个进程、chrome 63MB / rustc 1.3GB），是展示层崩了。

E2E 没抓到是因为测试目录只有单一 python 进程（events 与 write_bytes 同名，cur 永不为 null）。

## 修复

- 两处合并对 `cur` 做 null 处理（`cur?.Path ?? ""`、`cur?.EventCount ?? 0`、LastActivity 取较晚者）。
- 新增 `UnifiedQueryTests` 两个回归用例：进程/文件夹"仅存在于 write_bytes"时查询不抛异常且正确入榜（xunit 67 绿）。

## 验证

- 对 v0.9.1 当天真实库跑修复后的合并逻辑：榜单 **76 个进程**（rustc 1349MB、dotnet 303MB、nvcontainer 257MB、node 255MB、chrome 64MB、飞书/微信…），此前因 NRE 整表为空。
- 0.9.2 已替换 publish_v91 目录的 exe（保留当日数据库），启动 READY、主窗口 10ms 应答。
- 干净单文件归档在 publish_v92。

## 教训

后台查询的异常不能只写 Debug.WriteLine——会让"数据有、界面空"无声发生。后续应把后台查询异常计数并在 UI 状态行提示。
