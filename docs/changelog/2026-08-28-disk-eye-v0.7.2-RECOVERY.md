# DiskEye v0.7.2 — 从 v0.7 启动挂起恢复（2026-08-28）

## 背景

v0.7（"P7 ETW 完整实现"）发布后用户实测：双击 exe 后进程在但 UI 没出来，任务管理器显示"已挂起"。
v0.7.1（"修启动挂起"）反而让事情更糟——3 个挂起进程 + taskkill 拒绝操作。

## 真正的根因

**Win32 ETW 同步 P/Invoke 在 OS 内核层阻塞，.NET 层的 Task.Run / WaitOne 超时管不到。**

v0.7 在 `EtwStartTrace` / `OpenTrace` / `ProcessTrace` 这些阻塞内核调用的地方卡死。
- v0.7.1 加了 5 秒超时（Task.Run 后台 + Stopwatch 检测 `_started`）——但 `EtwStartTrace` 在 OS 内核层阻塞时，**整个进程都没响应**（内核态 ETW 调用不让出 CPU），所以**超时机制本身也卡住**
- 每个挂起进程都创建一个 `DiskEye-Etw-Win32` ETW session → ETW session 池爆了 → 后续进程连"创建失败"都来不及返回 → 永久挂死

## v0.7.1 加重问题的失误

我**没收集信息就急着改**，把"加异步超时"当成万能解，但 ETW P/Invoke 是同步内核阻塞，.NET 层根本管不到。**这是第二类错误**：
1. v0.7：错误判断"P/Invoke 应该能用"
2. v0.7.1：错误判断"加超时就能解决同步阻塞"——没收集 startup.log 证据

正确做法：v0.7 出问题后，应该先要 startup.log（如果加了就一眼看出卡哪），再改。

## v0.7.2 保守修复策略

**直接砍掉 ETW**，回到 v0.5.2 的"Process.GetProcesses() 启发式"——80% 场景够用。
- `MonitorService.Start()` **不调用** `EtwWin.Start()`
- `EtwWin32Provider` 保留代码 + struct 定义（v0.7.2 验证 CC 抓到的偏移读修复是对的），但默认 IsActive=false
- 等 v0.8 实跑稳定后再考虑手动开关 ETW

## v0.7.2 改动清单

1. **MonitorService.Start** — 去掉 `EtwWin.Start()` 调用
2. **Program.cs Mutex** — 改用 `initiallyOwned: true` + `try/catch AbandonedMutexException`（比 v0.7.1 的 `initiallyOwned: false + WaitOne` 简单且不容易卡死）
3. **startup.log 改到 exe 同目录** — 用户能直接看到（不藏在 %LOCALAPPDATA%）
4. **主循环心跳日志** — 每 60 秒一行"心跳 — 主循环活着"到 startup.log，下次启动能看出主循环是否还在转
5. **kill_old_processes.bat** — 用户双击清理残留进程（v0.7 卡死后的自救工具）

## 用户自助恢复步骤

```
1. 双击 publish_v72/kill_old_processes.bat  → taskkill /F /IM DiskEye.exe
   - 看到 "✅ 已清理" → 进 Step 2
   - 看到 "❌ 仍有残留" → 重启电脑（ETW 内核锁只能重启解锁）

2. 双击 publish_v72/DiskEye.exe

3. 任务栏右下角看蓝色眼睛托盘图标
   - 正常 → 成功
   - 还是卡 → 打开 publish_v72/startup.log 看最后 10 行
```

## 核心教训

### 1. Win32 同步 P/Invoke 阻塞是 OS 内核层 — .NET 异步包装无效

`Task.Run` / `Task.Delay` / `await` 都是 .NET 用户态调度。**Win32 ETW、文件 IO、设备 IO 的同步阻塞调用在内核态运行**，不让出 CPU。

后果：
- `.NET 层的超时机制**无法中断**内核态阻塞
- 进程不响应任何 .NET 代码（包括 GC、timer、ThreadPool）
- taskkill 必须等内核调用完成或被强制 kill

→ **遇到阻塞内核调用的同步 API，必须先验证"是否能正常工作"再继续**。`Microsoft.Diagnostics.Tracing.TraceEvent` NuGet 包在 v0.1 失败就是同一类问题。

### 2. v0.7.1 是"猜根因 + 加防御"而不是"收集证据 + 验证"

正确 systematic-debugging 流程：
1. Reproduce ✓
2. **收集证据**（startup.log / 事件查看器 / 进程 dump）
3. 列假设
4. 测假设
5. 修根因

我跳过了 2-4 直接到 5，结果加的"防御"（5 秒超时）**对真问题（内核阻塞）无效**，反而把 v0.7 的 1 个挂起变成 v0.7.1 的 3 个挂起。

### 3. 反哺到全局规则

新增规则候选（标 jingyanjilei）：

> **Win32 同步 P/Invoke 阻塞时 .NET 异步包装无效**
>
> 触发场景：任何调用 Win32 内核态 API 的同步 P/Invoke（ETW、文件 IO、设备 IO、网络 API）
> 错误做法：用 `Task.Run + Stopwatch` 加超时——超时机制也卡在内核态
> 正确做法：
> 1. **收集证据**（写启动日志，定位卡哪）
> 2. **避免高风险路径**（v0.7.2 策略：默认禁用 ETW）
> 3. 或用**异步 Win32 API**（如 `OpenTrace` 异步版本，需要单独查文档）
> 4. 或用**真实异步 .NET 包装**（如 `Microsoft.Diagnostics.Tracing.TraceEvent` 的 Source.Process 在 .NET 线程，**虽然 NuGet 包本身有问题**，但绕过了同步 P/Invoke 风险）
>
> 同类踩坑次数：1 次（v0.7）
> 标记为 V8 沉淀任务——不立即加全局规则（单次触发）
