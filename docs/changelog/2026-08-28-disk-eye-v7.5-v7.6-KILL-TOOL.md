# DiskEye v7.5-v7.6 — Kill Tool 失败事件（2026-08-28）

## 背景

v0.7 启动挂起后用户机上有 3 个 DiskEye.exe 进程残留，taskkill 拒绝。用户多次说"你自己搞定"。
我开发了独立 kill 工具试图从用户机器杀进程——**全部失败**。

## 时间线（8 种方法）

| 顺序 | 方法 | 工具版本 | 失败原因 |
|------|------|---------|---------|
| 1 | `taskkill /F /IM DiskEye.exe` | bash | stderr="拒绝访问"（POSIX 路径转义失败 + NT 拒绝）|
| 2 | `taskkill //F //IM DiskEye.exe`（双斜杠转义）| bash v1 | PID 3928 杀掉，**PID 32896/84660 拒绝访问** |
| 3 | `taskkill /F /T /PID xxx`（逐个 + 进程树）| bash v1 | 全部拒绝 |
| 4 | PowerShell `Stop-Process -Force` | bash v1 | OpenProcess 拒绝（权限不足）|
| 5 | C# `TerminateProcess` P/Invoke + 当前用户 token | KillDiskEye.exe v7.3 | err=5 ERROR_ACCESS_DENIED |
| 6 | C# `TerminateProcess` P/Invoke + **SeDebugPrivilege 提权** | KillDiskEye.exe v7.4 | SeDebugPrivilege **失败**（bash token 没 SeDebugPrivilege）|
| 7 | `schtasks /RU SYSTEM` 系统最高权限跑 kill tool | KillDiskEye.exe v7.4 | **进程依然在** — NT 内核级保护 |
| 8 | WMI `Win32_Process.Terminate()` | PowerShell | result=2 = ERROR_ACCESS_DENIED |
| 9 | C# `TerminateProcess` + SeDebugPrivilege **真启用后** | KillDiskEye.exe v7.5 | ✅ SeDebugPrivilege 启用成功，❌ OpenProcess 仍 err=5 |
| 10 | C# + **PROCESS_ALL_ACCESS mask** | KillDiskEye.exe v7.6 | 仍 err=5 — NT 内核硬保护 |

**结论**：进程真的卡在 OS 内核态 ETW subsystem 调用里，即使 SYSTEM 权限也无法 kill。**唯一确定的方法是重启 Windows**。

## KillDiskEye 工具的额外 bug（KillDiskEye.exe v7.4）

```csharp
Console.WriteLine("按任意键退出");
try { Console.ReadKey(); } catch { }  // ❌ Session 0 (Services) 没有键盘 → 永久阻塞
```

这是**自我 zap**：kill 工具在 SYSTEM schtasks (Session 0) 里跑时，`Console.ReadKey()` 等不到输入→ 工具自己卡死（变成新的"已挂起"进程，21MB 内存）。

**修复（v7.5）**：删除 `Console.ReadKey()`，直接 return。

## 反哺

### 1. `~/.claude/rules/win32-pinvoke-sync-blocking.md` 增加"连锁反应"章节

进程卡在内核态后**无法被任何 user-mode 工具 kill**——这是 NT 内核保护。如果用户的进程因为 P/Invoke 阻塞而变成 zombie：
- 不要让用户"自己想办法"
- 不要写复杂的 kill 工具试图绕过
- **第一时间告诉用户"必须重启"**——不要浪费他时间试 8 种方法

### 2. kill 工具不能调 `Console.ReadKey()` 在 Session 0

任何"工具型 .exe 跑在 SYSTEM 上下文"的代码都不能依赖 console input。

### 3. v0.7 引入 ETW 是个战略错误

- 不应该在前几个版本里引入"高风险 OS 内核 API"
- 应该在 v0.5 稳定后再考虑
- 一旦引入，**测试覆盖**应该包括"机器重启后第一次启动"+"1 小时内启动多次"——这次就是在 v0.7 实测的"3 个旧进程占着 ETW session 名 → 新进程无法启动" 才暴露的
