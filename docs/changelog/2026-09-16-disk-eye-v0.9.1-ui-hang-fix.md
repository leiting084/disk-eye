# DiskEye v0.9.1 — UI 无响应修复 + 风暴归因补齐（2026-09-16）

v0.9 发布后实测（publish_v90 运行约 5 小时）暴露的回归与短板，本版修复。

## 现场证据

- startup.log 心跳 03:36 后停近 2 小时，03:00 出现 5 条心跳在 3 秒内连发 → UI 消息泵冻结、Timer 事件积压。
- events 111,574 行，pending 35%（39,198）；活跃 pid 872 个；write_bytes 中 unknown 4,329 行。
- 用户现象：主窗口无响应、X 关不上（实际是消息泵卡死，关闭消息排不上队；X 设计本为缩托盘）。

## 根因

1. **UI 线程被 WMI 拖死**：v0.8 的 `QueryProcessTree` 对当天每个 pid（872 个）各发一次 WMI 查询（2s 超时），且在 UI 线程随 3 秒刷新同步执行；v0.9 又在同线程叠加 write_bytes 全表 GROUP BY。卡一次数分钟。
2. **回填在 ETW 读帧线程同步写库**：风暴时 DB I/O 拖慢帧消费，部分帧晚于 10 秒 pending 回填窗口 → 永久 unknown。
3. **榜单丢了"无写入活动"**：v0.9 把凶手指控榜/文件夹的事件数也换成 write_bytes 样本数，违背自己 design（design 写的是事件数仍用 events），导致只删除/改名不写字节的进程从榜单消失。

## 修复

- **所有 SQLite/WMI 查询移出 UI 线程**：RefreshData 改为后台 Task 取数 + BeginInvoke 回 UI 线程填表，单飞去重（_refreshRunning），dispose/句柄竞态有防护。UI 不再被查询阻塞。
- **进程树 WMI N+1 → 单次全量枚举**：一次 `SELECT ProcessId,ParentProcessId` 建 pid→ppid 映射（整体 8 秒超时，失败降级空），名字优先用 DB 已记录值（进程退出也有名），缓存 5s→30s。
- **回填移到 pump 线程**：ETW 读帧只入队，100ms pump 批量 BackfillRows；pending 回填窗口 10s→30s、容量 5 万→10 万。
- **新增 `BackfillNamesByPid`**：每 60 秒后台用"同 pid 已知名字"补全 events/write_bytes 的 unknown（风暴后自愈）。
- **榜单恢复双口径**：新增 `QueryProcessUnified/QueryFolderUnified`——事件数来自 events（含删除/改名），写入字节来自 write_bytes；列同时保留"事件数/写入字节"。
- 心跳日志不再误导（今日字节来自 write_bytes 实时累计）。

## 验证

- 65 xunit 全绿。
- 60 秒 6,000 事件/秒风暴压测运行中的发布版：**风暴窗归因率 100%（1,233/1,233，零 pending）**，write_bytes unknown=0。
- UI 探针（experiments/ui_probe.ps1，WM_NULL SendMessageTimeout）：主窗口连续 4 次 10–12ms 应答；200 文件写入 + 多刷新周期下 Responding=True；X 正常缩托盘。
- 进程树对 800+ pid 不再卡（单次 WMI + 30s 缓存）。
