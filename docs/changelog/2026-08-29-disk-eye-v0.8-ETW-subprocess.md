# DiskEye v0.8 — ETW 子进程隔离重做 + v0.7 事故真根因（2026-08-29）

## 一句话

ETW 精确反查以**独立子进程**形态回归：主程序零 ETW 调用，子进程卡死/崩溃只影响精确度，自动降级启发式。实机验证全部通过。

## v0.7 卡死事故的三个隐藏根因（本次实测定论）

v0.7.2 把锅全甩给"Win32 同步 P/Invoke 内核阻塞"。这次重做时做了对照实验，发现真相更具体：

| # | 根因 | 证据 |
|---|------|------|
| 1 | **provider GUID 写错**：用了 `{bdd372b7-…}`，真正的 Microsoft-Windows-Kernel-File 是 `{EDD08927-9CC4-4E65-B970-C2560FB5C289}` | `logman query providers` 实测 |
| 2 | **关键字写错**：FileIO = `0x20`，不是 `0x10`（0x10 是 FILENAME） | 同上 |
| 3 | **手写的 EVENT_TRACE_LOGFILE / EVENT_TRACE_PROPERTIES 布局全错**：struct 里凭空多了 TotalEvents 字段导致整体偏移错位；回调字段真实偏移 424，v0.7 写的位置是错的；`EtwStartTrace` 这个导出根本不存在 | 本机 SDK `evntrace.h` 逐字段比对 + AccessViolation 实验 |

结论：**就算 v0.7 不卡死，它也收不到任何文件事件**。卡死只是表象，P/Invoke 层从 GUID 到结构体没有一处是对的。

### 附带发现

- 用户机器装了 **360 安全软件**（ZhuDongFangYu.exe 等）。一度怀疑它 hook 了 StartTrace（手写 P/Invoke 返回 161 ERROR_BAD_PATHNAME，logman/PowerShell 却正常）。但 TraceEvent 库从同一进程建 session 成功 → 360 不拦正确调用，161 是我自己的布局问题。
- FileIo/Create（EventId=12）payload 布局实测：偏移 0 IrpPtr(8) / 8 FileObject(8) / 16-31 元数据 / **32 起 Unicode 路径**（`\Device\HarddiskVolumeX\…` NT 形式，需 QueryDosDevice 转 DOS）。
- FILEIO 关键字事件量：全机约 20 条/秒，轻松。

## 架构

```
DiskEye.exe (主程序, WinForms, 0 ETW 调用)
   │  spawn DiskEye.Etw.exe <父PID>，RedirectStandardOutput，CreateNoWindow
   ▼
DiskEye.Etw.exe (子进程, TraceEvent 库)
   │  stdout 行协议: READY / EV <pid>\t<path> / HB(5s) / ERR <msg>
   ▼
主进程 EtwChildProvider: 异步读 → 1.5s TTL 缓存 → Resolve(path)→pid
```

安全设计：
- 主进程对子进程**只有异步管道读**，`Start()` 立即返回不阻塞（READY 到达前自动走启发式）
- 看门狗：15s 无心跳或进程退出 → Kill + 降级 + startup.log 记录；60s 冷却后最多重启 1 次
- 子进程带**父 PID 看门狗**：父进程被杀 10s 内自我 Dispose session + 退出（实测验证）
- 同名孤儿 session 由 TraceEventSession 构造时自动停旧建新
- `config.json` 新增 `EnableEtw`（默认 true），出问题可手工关闭兜底

## 改动清单

1. **新增 `src/DiskEye.Etw/`** — TraceEvent 库消费 Kernel-File/FileIO，stdout 协议，父进程看门狗
2. **新增 `src/DiskEye/Monitoring/EtwChildProvider.cs`** — 子进程生命周期管理 + 事件缓存（同路径 TTL 内先到先得：实测杀软/RuntimeBroker 会尾随创建者打开新文件），表面与旧 Provider 一致
3. **删除 `EtwWin32Provider.cs`** — 手写的坏 P/Invoke 全部废弃
4. **`MonitorService`/`EventAggregator`** — 换类型接线，`EnableEtw` 开关
5. **`EventAggregator` 反查时机修复** — ETW 事件经内核缓冲区 flush（~1s）才到，入队时立即反查必然错过；改为入队存原始事件，flush 时给 ETW 最长 2s 匹配窗口，超时才走启发式（实测 1.2s 会边际踏空：刚好错过则退化到启发式乱猜，窗口必须留足余量；缓存 TTL 相应提到 2.5s）
6. **进程名随事件解析** — 子进程在事件到达时立刻把 pid→名字解析好一并发来（`EV pid\tname\tpath`），短命进程退出后也能留下名字
7. **修复 `TrayIconManager.cs:159`** — `DeleteObject` 误从 user32.dll 导入（正确是 gdi32.dll），**这是"一个劲报错"的主因之一：启动即崩 EntryPointNotFoundException**
8. **`AppConfig`** 新增 `EnableEtw`
9. **`publish.bat`** — 固化两步发布，产出 `publish_v80/`（DiskEye.exe + DiskEye.Etw.exe）

## 教训更新

v0.7.2 复盘里的"Win32 同步 P/Invoke 阻塞 .NET 管不到"依然成立，但要补一条更根本的：

> **手写 P/Invoke 的 GUID/常量/结构体必须对照本机 SDK 头文件逐一验证，并用对照实验（logman/PowerShell/官方库）先证伪"环境不支持"，再怀疑"系统设计"。** v0.7 把"调用写错"误诊成"内核阻塞"，导致 v0.7.2 的保守回退其实砍错了方向——正确做法是换可信实现（官方 TraceEvent 库）+ 进程隔离兜底。
